# RFC 23 — Control message batching

**Covered RFC 23. Next RFC 24 — Documentation Conventions.**
This lab reuses the [RFC 22 decoder](https://github.com/Sreenivas-Sadhu-Prabhakara/rfc-0022-control-decoder/commit/af66ff792d752cccc237c30a71aba4b2c3698625)
for command widths and ordered decoding.

George Gregg of UCSB proposed on 16 October 1969 that early ARPANET
hosts batch control messages queued for the same remote host while the
link waited for Ready for Next Message (RFNM). Once ready, the sender could
transmit them together. The receiver would decode and act on each command
until it exhausted the communication. RFC 23 is a historical memo.
The RFC Editor lists it in the Legacy stream with status Unknown and
no formal update or obsolescence relationships in either direction.

- [Official RFC text](https://www.rfc-editor.org/info/rfc23/)
- [RFC Editor metadata](https://www.rfc-editor.org/rfc/rfc23.json)

## Applications

- **Gateway control queue lab.** Replay an acknowledgment-limited link
  and compare one-command sends with batching on readiness.
- **Banking integration testing.** Measure the effect of combining already
  queued adapter commands for one downstream peer.
- **Cloud controller testing.** Confirm that a byte cap preserves command
  boundaries and ordering across batches.

## Run

Use Go 1.22 or newer from the repository root.

```sh
go run ./cmd/batch23 < examples/burst.json
go run ./cmd/batch23 -html < examples/burst.json > docs/index.html
go test -race ./...
go vet ./...
go build ./...
```

The sample drains five commands with five sends in the baseline and three
with batching. The final ready tick moves from 20 to 12, and the longest
queue wait falls from 11 to 3 ticks.

## Model

One remote host, one in-flight send, and a fixed acknowledgment delay.
An idle link sends immediately. When it becomes ready, arrivals at that
tick are eligible. The batch takes the longest FIFO prefix that fits the
byte cap and leaves entire commands queued when they do not fit. The
receiver runs the RFC 22 decoder over each concatenated teaching payload.
A valid payload produces a trace of commands in order.

The simulator accepts one JSON object up to 64 KiB. Supply an acknowledgment
delay of 1–10000 ticks, a byte cap of 2–1024, and 1–500 arrivals in nondecreasing
tick order from 0 through 1000000. Each arrival is one RFC 22 command written
as space-separated hexadecimal octets. Invalid input produces no report.

The byte cap, deterministic event ordering, and fixed delay are modeling
choices. The lab illustrates send scheduling and byte boundaries. Historic
packet headers, actual RFNM signaling, command side effects, retries, and
production latency measurements are outside the exercise. GitHub Pages
serves the saved HTML generated by the local simulator.
